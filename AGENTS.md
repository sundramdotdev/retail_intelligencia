## 1. Non-Negotiable Core Principles

1. **Hardware-First Physical AI Principle**:
   Retail Intelligencia is a **hardware-first edge AI retail intelligence platform**. The physical edge computing node connected to retail cameras is the core product. The software platform (backend, database, realtime layer, dashboard) exists solely to configure, ingest, validate, store, alert, and enable human staff action upon the intelligence generated by the edge hardware.
   * Do NOT treat this platform as "a SaaS dashboard with AI slapped on."
   * Respect the flow: `SENSE → UNDERSTAND → DECIDE → ACT`.

2. **Strict Hardware / Software Boundary**:
   * Computer vision inference, frame decoding, object detection, object tracking, zone occupancy computation, and deterministic retail event generation **MUST occur locally on the edge device**.
   * Never stream raw video feeds to the cloud or dashboard during standard operation.
   * Edge devices communicate with the backend exclusively via standardized JSON events over MQTT (primary) or HTTPS fallback.

3. **Common Retail Event Contract**:
   * Every single edge observation converted into an event MUST conform strictly to the canonical `RetailEvent` envelope defined in [docs/contracts/retail-event-contract.md](file:///c:/hackathon/retail_intelligencia/docs/contracts/retail-event-contract.md).
   * **NEVER invent ad-hoc event payloads**, parallel event envelopes, or bypass the `RetailEvent` schema.

4. **Service Boundary & Database Stack**:
   * System architecture: `FastAPI (Device Gateway) → Node.js/TypeScript Data Service (Prisma) → PostgreSQL`.
   * **NEVER execute Prisma directly from Python/FastAPI**. FastAPI interfaces with the backend data layer via internal service contracts or delegates data persistence to the Node.js/TypeScript Data Service.
   * The database is strictly normalized and managed via the TypeScript Prisma schema.

5. **Privacy by Design**:
   * **NO FACIAL RECOGNITION**.
   * **NO FACIAL EMBEDDINGS**.
   * **NO CUSTOMER IDENTITY RE-IDENTIFICATION**.
   * Tracking IDs generated on the edge (`track_id`) are ephemeral, localized to the camera field of view, and discarded when the subject leaves the zone. They are NOT persistent biometric customer identifiers.

6. **Deterministic MVP Rules Over Generative LLMs**:
   * MVP operational retail conditions (`SHELF_LOW_STOCK`, `SHELF_EMPTY`, `QUEUE_HIGH`, `TRAFFIC_HIGH`, `TRAFFIC_LOW`, `ZONE_DWELL`, `DEVICE_HEALTH`) must be detected and generated via **deterministic computer vision models and rule engines**.
   * Do NOT introduce generative LLMs into the real-time detection, queue counting, or event emission pipeline.

7. **Idempotency & Deduplication**:
   * Network retries and edge reconnects mean the backend will receive duplicate events.
   * Every event consumer in the backend MUST be idempotent based on `eventId`. Duplicate `eventId` records must never create duplicate alerts, tasks, or metrics.

8. **Offline Resilience**:
   * Edge AI inference must NEVER halt when cloud or local network connectivity drops.
   * The edge node maintains a local ring buffer (SQLite / WAL) and replays unacknowledged events upon reconnection.

## 3. Strict Prohibitions ("Do Nots")

* ❌ **DO NOT** write application code before the corresponding Phase is officially unlocked.
* ❌ **DO NOT** use Prisma directly from Python.
* ❌ **DO NOT** stream raw video to the dashboard or backend cloud servers.
* ❌ **DO NOT** bypass the edge device by sending simulated raw bounding boxes to the cloud for inference.
* ❌ **DO NOT** create parallel MQTT topic hierarchies. Use only `retail/{environment}/{storeId}/{deviceId}/...`.
* ❌ **DO NOT** implement facial recognition, demographic profiling, or persistent customer re-identification.
* ❌ **DO NOT** hardcode secrets, private keys, or API tokens into any file or documentation.
* ❌ **DO NOT** create fake AI detections or mock data that masks hardware/model failures.
* ❌ **DO NOT** modify the `RetailEvent` envelope without formal schema version increment (`schemaVersion: "2.0"`).

## 4. Phase Roadmap Reference

Agents must know what phase the repository is in before proposing changes:

* **Phase 0 — System Definition (CURRENT PHASE)**: Architecture freeze, contracts, schemas, protocols, boundaries, documentation. No application features.
* **Phase 1 — Repository & Development Infrastructure**: Monorepo/polyrepo tooling, linters, CI/CD, local dev environment.
* **Phase 2 — Edge Device Foundation**: OS image, hardware acceleration runtimes, device daemons, local storage.
* **Phase 3 — Computer Vision Runtime**: Stream decoders, YOLO/object detection, ByteTrack tracking, zone projection.
* **Phase 4 — Retail Intelligence Engine**: Shelf heuristics, queue counter, dwell estimator, `RetailEvent` generator.
* **Phase 5 — Device Communication**: MQTT client, mTLS, local ring buffer, heartbeat, health telemetry daemon.
* **Phase 6 — Backend & Data Platform**: FastAPI Gateway, Node.js Data Service, Prisma, PostgreSQL, business rule engine.
* **Phase 7 — Realtime Dashboard**: Next.js UI, TailwindCSS/Vanilla CSS, WebSocket/SSE subscription, interactive live store map.
* **Phase 8 — Staff Action System**: Alert dispatch, task assignment workflow, mobile-responsive triage view.
* **Phase 9 — Analytics, Testing, Optimization & Deployment**: End-to-end integration, performance tuning, pilot readiness.

**If you are asked to implement code for Phase 1 through 9 while Phase 0 is active, reject the request and direct focus to completing Phase 0 requirements first.**
